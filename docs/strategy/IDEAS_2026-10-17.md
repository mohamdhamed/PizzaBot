- **التنفيذ:** إما كل مطعم بحساب Stripe/Satispay خاص بيه (key في إعدادات المطعم)، أو **Stripe Connect** (PULSAR = platform، وممكن application fee لاحقاً بشكل قانوني).

- **الاقتراح:** v1 = الدفع عند الاستلام بس. الدفع أونلاين في v2.
- يتأكد مع المحاسب، خصوصاً لو فيه عمولة على الطلبات.

## 3. السيرفر: الأداء والاعتمادية

### الأداء
- تقدير: 100 مطعم × 150 طلب × 20 ضغطة ≈ **30–40 request/ثانية في الذروة** → السيرفر (4 ARM, 23GB) يستحمل بسهولة.
- تقريبياً: 1–50 مطعم مفيش مشكلة، 50–300 مريح، 300–1000 محتاج ضبط.

### الحدود الحقيقية
- **Telegram:** ~30 رسالة/ثانية لكل بوت → **بوت لكل مطعم**.
- WhatsApp: حدود لكل رقم ومستوى verification.
- السيرفر مشترك مع `BotBudget` و`openclaw` و`postgres` → حدود memory/CPU لكل container.

### الاعتمادية (الأهم)
- Oracle Always Free: مفيش SLA، وممكن يسترجع instances خاملة. Single point of failure.
- **قبل أول مطعم يدفع:** backup يومي لـ PostgreSQL برة السيرفر، monitoring (Uptime Kuma / Healthchecks)، fallback برقم تليفون المطعم.

### الترقية للمدفوع ❓
1. **دلوقتي:** ترقية Oracle لـ **Pay As You Go** (الـ Always Free يفضل ببلاش، ومفيش reclaim للـ idle) + **budget alert**.
2. **أول مطعم يدفع:** backups برة Oracle (Hetzner Storage Box / Backblaze / البيت).
3. **~20–30 مطعم:** سيرفر **Hetzner CAX (ARM)** كـ standby أو production. بدائل: Netcup, OVH, **Aruba** (ميزة "i dati restano in Italia").
- الفواتير باسم PULSAR SERVICE S.A.S. + reverse charge مع المحاسب.

## 5. القنوات (Channels)

### البدائل
1. **صفحة طلب ويب / PWA** (لينك أو QR، من غير تطبيق ولا حساب) ⭐
2. QR على الترابيزة
3. زرار "Ordina online" في Google Maps
4. Kiosk/تابلت عند الكاونتر (مؤجل)
5. مساعد صوتي على التليفون (محتاج LLM — مؤجل)

### ملاحظات
- **WhatsApp أهم من Telegram في إيطاليا بكتير.**
- الـ state machine مستقلة عن الـ channel → أي قناة = adapter جديد.
- صفحة الويب لوحدها: مميزات (شغالة مع الكل، مفيش Meta verification) وعيوب (مفيش هوية تلقائية → OTP/SMS أو تأكيد بالتليفون، مفيش تحديثات تلقائية → صفحة متابعة/SMS، الزبون مش بيرجع → PWA و"Riordina"، حماية من spam).
- ❓ قرار: الويب بنفس أسلوب الأزرار (أسرع) ولا صفحة منيو بسلة (أحلى، frontend أكتر)؟
- **ملاحظة محمد:** صفحة ويب لوحدها = زي أي حد في السوق. التميّز لازم ييجي من حاجة تانية (§6، §8، §9).

## 6. البوت الذكي (LLM)

### الفكرة
الرؤية الأصلية كانت **بوت يفهم الزبون**. الـ LLM اتشال من v1 بسبب خطر الفلوس، مش لأن الفكرة غلط.

### التصميم الآمن المقترح ❓ (تعديل محتمل للقرار الثابت رقم 1)
1. الزبون يكتب أو يبعت **رسالة صوتية**.
2. الـ LLM يحوّلها لـ **IDs من المنيو بس** (من غير أسعار ولا نص للزبون).
3. الكود يتحقق من كل ID ويحسب **السعر من الـ DB**.
4. الزبون يشوف **ملخص بأزرار** ✅ Conferma / ✏️ Modifica.
5. لو مافهمش → يرجع للأزرار.

صياغة مقترحة للقرار: *"الـ LLM مسموح كـ parser بس، يطلّع IDs بتتراجع على الـ DB، ومفيش سعر ولا نص للزبون منه، والتأكيد دايماً بالأزرار."* — **لسه ماتكتبتش في `CONTEXT.md`.**

### نقاط التميّز
- **الرسايل الصوتية على WhatsApp** (vocali).
- **"Il solito"**.
- أسئلة طبيعية عن المنيو والـ allergens من الـ DB بس.
- لاحقاً: الرد على التليفون.

### محلي ولا API
- **محلي:** Ollama / llama.cpp + whisper.cpp للصوت. ببلاش وخصوصية، بس بطيء على CPU ومشكلة في الذروة.
- **API:** سريع ورخيص (أقل من سنت للطلب تقريباً). نبعت نص الطلب بس من غير PII، و provider بمعالجة في أوروبا و DPA.
- التصميم: interface واحد `OrderParser` قابل للتبديل. الاقتراح للـ production: **hybrid**.

### نتيجة تجربة 1 (local, `b7a81f2`)
| | qwen2.5 3B | qwen2.5 7B |
|---|---|---|
| الطلب كله صح | 6/20 | 15/20 |
| السطور صح | 53% | 84% |
| IDs مش موجودة | 9 | 2 |
| Injection | فشل (ضيّع الطلب) | نجح |
| latency avg / p95 | 5.3s / 7.7s | 12.9s / 20.6s |
| RAM | 3.1 GiB | 5.8 GiB |
| 4 رسايل في نفس الوقت | 86s | 204s |

- **الخلاصة:** الأمان شغال (مفيش سعر/خصم/رد حر، وكل ID غلط اتمسك). المشكلة السرعة. **v1 يفضل من غير LLM.**
- الـ volume `pizzabot_ollama_models` (~6.6GB) لسه موجود على السيرفر.

### تجربة 2 (مكتوب الـ prompt، لسه ماتنفذتش / النتيجة ماوصلتش)
مقارنة على نفس الـ 20 حالة: **MatcherParser** (من غير موديل) / **LocalEnumParser** (7B + enum IDs + prompt أقصر) / **ApiParser** (`claude-haiku-5-5` عن طريق urllib، `ANTHROPIC_API_KEY` في `.env`) / **HybridParser** (matcher الأول ثم fallback). الناتج: `REPORT_COMPARISON.md` على نفس الـ branch.

## 7. الطلب والمطعم مقفول (Pre-order)

- **نفس اليوم** على slots الفتح (الأسهل، ومطلوب) ⭐
- **أيام قدام** (حفلات/مكاتب) — بيكسر [A9]، مؤجل.
- **وضع Pausa** وقت الزحمة ⭐
- محتاج: إعدادات لكل مطعم (يقبل؟ كام يوم؟ أقصى طلبات لكل slot)، status جديد (`scheduled` / `pending_confirmation`)، رسالة واضحة للزبون، إشعار وقت الفتح، سياسة إلغاء، حماية من الـ no-show.

- الاقتراح: نفس اليوم + Pausa في v1، بعد خطوة Channel + PostgreSQL.

## 9. PizzaBox (هاردوير المطبخ)

### المكونات (تقريبية — الأسعار تتراجع وقت الشراء)
| الجزء | الاختيار | السعر التقريبي |
|---|---|---|
| طابعة حرارية 80mm ESC/POS + Ethernet | Epson TM-T20III / TM-m30، Star TSP143 (أو Munbyn/Xprinter للتجربة) | €150–300 (€60–120 الرخيص) |
| كمبيوتر | Raspberry Pi 4/5 + علبة + باور + SSD أو كارت high-endurance | €80–130 |
| 4G احتياطي | راوتر صناعي (Teltonika RUT) أو USB dongle + شريحة IoT | €100–150 + €2–5/شهر |
| تحكم | زراير فيزيكال (Accetta / Pausa) + buzzer | بضع يوروهات |
| اختياري | شاشة لمس 7" (KDS صغير) | €60–90 |
| **الإجمالي** | | **€250–450** |

### الاتصال
- الجهاز **هو اللي بيتصل** بالسيرفر (WebSocket/HTTPS) — مفيش فتح بورتات.
- **token لكل جهاز** مربوط بـ `restaurant_id`.
- تأكيد استلام وطباعة، ومفيش طباعة مكررة (ID فريد).
- **Heartbeat** كل 30s → تنبيه لو الجهاز اختفى أكتر من دقيقتين.
- Queue محلي + تحويل أوتوماتيك لـ 4G.
- **بديل أبسط:** طابعات Epson Server Direct Print / Star CloudPRNT تسحب من السيرفر من غير Pi (باقة أساسية).

### الإدارة
Tailscale للوصول، تحديثات مركزية، نظام read-only، صفحة حالة لكل الأجهزة.

### التجاري
- **Comodato d'uso** (إعارة) + ضمان صغير. يرجع لو الاشتراك اتلغى.
- €300 / 24 شهر ≈ €12.5/شهر → جوه باقة €99.
- أجهزة جاهزة ومعتمدة (CE)، مش جهاز من الصفر.

### الخطة
1. Prototype في البيت (Pi + طابعة رخيصة + المطعم الـ demo).
2. مطعم حقيقي لمدة شهر.
3. 4G + زراير + إدارة عن بعد.
- يعتمد على وجود الطلبات في PostgreSQL → بعد خطوة Channel + PostgreSQL.

## 10. منتج تاني: المخزون والصلاحيات (باكيدج PULSAR)

### المشكلة (من مطعم حقيقي)
- مفيش جرد منظم. حد بينزل يدوي يشوف الحاجات اللي هتنتهي ويطلّعها قدام.
- صاحب المطعم بيجي كل 2–3 أيام يبص على المخزن بنفسه، ويكتب الناقص، ويطلب من الموردين.

### الفكرة: منتجات منفصلة بتشتغل مع بعض
1. **🏷️ Scadenze:** ليبل يتطبع عند الاستلام/الفتح (اسم، تاريخ، صلاحية، QR)، رسالة يومية بالحاجات اللي هتنتهي، FIFO أوتوماتيك.
2. **📦 Scorte e ordini:** جرد سريع بالأزرار (نفس الـ guided flow)، حد أدنى لكل صنف، **مسودة طلب لكل مورد** على WhatsApp/إيميل بموافقة بضغطة.
3. **🍕 الربط بالطلبات:** وصفة تقريبية لكل صنف → استهلاك متوقع من طلبات PizzaBot → "الموتزاريلا هتخلص بكرة".
4. **🌡️ HACCP وحرارة التلاجات:** حساسات لاسلكية، سجل أوتوماتيك جاهز للتفتيش (ASL/NAS)، تنبيه بالليل. **إلزامي قانونياً** → سهل البيع، وفيه هاردوير.

### السوق في إيطاليا
- موجود: تطبيقات HACCP إيطالية زي **SimpleHACCP** (حرارة، صلاحيات، مخزن، allergens، ليبلات، تقارير للتفتيش)، ومنافسين أوروبيين زي Octopus HACCP. حساسات Bluetooth رخيصة (~€50) وأنظمة احترافية (testo Saveris). الـ gestionali فيها modules للمخزن بس معقدة وغالية على البيتزاريا الصغيرة.
- **الفجوة المحتملة:** "fatto per te" (تركيب وإعداد وخدمة)، **من غير تطبيق** (أزرار على WhatsApp/Telegram)، **الطلب من الموردين أوتوماتيك**، **الربط بطلبات PizzaBot**، باكيدج واحدة وحد واحد تتصل بيه.
- **ماتبنيش نسخة تانية من SimpleHACCP.**

### الخطوات المقترحة
1. **مقابلة صاحب المطعم الأول:** أكتر حاجة بتوجعه؟ بيخسر كام من البضاعة المنتهية؟ كام ساعة في الجرد والطلب؟ مين الموردين وإزاي بيطلب؟ يدفع كام؟ **جرّب برامج قبل كده؟ وسابها ليه؟**
2. ابدأ بأسهل منتج يبين نتيجة بفلوس: الصلاحية بالليبلات أو حساسات HACCP.
3. المطعم ده = أول عميل تجريبي (ببلاش/بخصم) مقابل feedback ومرجع.
4. **ماتشتتش:** PizzaBot الـ MVP الأول، والمخزون المنتج التاني على نفس الأساس.

**الصورة الكبيرة:** من "واحد عامل بوت" لـ **"PULSAR: الحلول الرقمية للبيتزاريا"** — طلبات ومطبخ ومخزون وHACCP.
